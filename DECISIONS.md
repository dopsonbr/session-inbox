## General

- G-001 — Scope is **local sessions on this Mac only** (CLI + Claude desktop's Code tab). No cloud sessions, no sync. User answered this in the doc's open questions.
- G-002 — The daemon is the only place that decides (classification, lifecycle, priority, notification policy, dedupe, reply routing). UI and shell render and send intents. Straight from the doc's guiding principle.
- G-003 — Bun is the language and runtime for everything that isn't Rust: daemon, hook, UI build, and all repo tooling (`scripts/*.ts` run with `bun`). No Node, npm, or shell scripts beyond one-liners. User instruction.
- G-004 — One Bun workspace: `apps/{daemon,hook,desktop}`, `packages/contracts`, `ops/`, `scripts/`, `fixtures/`. Matches the doc's repo layout.
- G-005 — Pin exact versions: `effect@4.1.2` (Foldkit 0.170 peers on `effect ~4.1.0`, `@effect/platform-bun` and `@effect/sql-sqlite-bun` are 4.1.2), `foldkit@0.170.0`, `@foldkit/ui@0.170.0`, `basecoat-css@1.1.0`, `tailwindcss@4.3.5`, `@biomejs/biome@2.6.6`, `typescript@5.9.3`. Doc says pin; 4.1.x is the one line all of them agree on.
- G-006 — TypeScript 5.9.3, not 7.x. Foldkit/Effect tooling is tested against 5.x; tsc is only used for `typecheck`, Bun runs TS directly.
- G-007 — Rust installed with Homebrew (`brew install rust`) because Tauri v2 needs cargo and none was present. Homebrew was already the machine's package manager; rustup can replace it later without code changes.
- G-008 — Work happens on short-lived branches per area (worktrees), merged to `main` often. User instruction: commit and merge frequently.
- G-009 — Testing is light and layered: pure unit tests (`bun test`) for domain transitions and UI update functions; fixture replay of real hook JSON against in-memory SQLite; a `scripts/smoke.ts` end-to-end run (daemon + hook binary + fake Claude payloads) that needs no Claude account. User asked for light ways to verify while building.
- G-010 — Delegation: Opus 5.5 (medium) for the daemon and the Foldkit UI (design-heavy, unfamiliar APIs); Sonnet 5.5 (medium) for the hook CLI, ops/install scripts, the Phase 0 spike and the Tauri shell (well-specified, mechanical). User instruction.
- G-011 — The daemon serves the built UI same-origin at `http://127.0.0.1:<port>/` and injects the bearer token into `<meta name="session-inbox-token">` (only after a Host-header check against DNS rebinding). The Tauri windows just load that URL, and so does a plain browser, so the UI needs no Tauri APIs and can be tested in any browser. The UI always calls relative `/v1/...`; in dev a proxy adds the header.
- G-012 — The shell, not the webview, consumes the daemon stream for native work: a Rust SSE client (`?client=shell`) posts notifications and sets the tray badge. Notifications then don't depend on a webview being alive, and the UI stays shell-agnostic.
- G-013 — The daemon itself opens "Open in Claude" URLs (`open <url>`); the shell needs no opener plugin. For CLI sessions with no URL, it copies `cd <cwd> && claude --resume <id>` to the clipboard.
- G-014 — Hold a PreToolUse only when Claude itself would have asked (permission_mode `default`, tool in the hold matcher, no matching allow rule in user/project/local settings, project not muted). AskUserQuestion is always held. Otherwise the inbox would add friction where Claude adds none.
- G-015 — Answering a pending AskUserQuestion goes back through its held PreToolUse hook (`allow` + `updatedInput.answers`, or `deny` + reason as a fallback the spike picks). `--resume -p` is only for idle/waiting sessions (free-text replies, non-live questions).
- G-016 — "Always allow" writes to `<project>/.claude/settings.local.json` `permissions.allow`, the same scope Claude's own "don't ask again for this project" uses. The user answered yes to writing Claude's settings; project scope keeps the blast radius small.
- G-017 — Session titles: the first prompt right away, then a 3–6 word title from `claude -p --model haiku` run with `SESSION_INBOX_INTERNAL=1` and hooks disabled so it's never ingested. The user answered "yes" to both options in the doc, so we do both: instant fallback, better title moments later.
- G-018 — Without a connected shell, the daemon falls back to `osascript` notifications (no actions) so "window closed ⇒ one notification within 2 s" holds even before the Tauri app runs.
- G-019 — Project = the main worktree root (via `git rev-parse --git-common-dir`). A session in a linked worktree records it in `session.worktree`, so all of a repo's worktrees group under one project.
- G-020 — `scripts/install.ts` is a dry run by default. It touches `~/.claude/settings.json` and launchd only with `--yes`, backs up first, and merges idempotently. Installing hooks globally changes every Claude session on the machine, so it's an explicit step.
- G-021 — Quiet hours are out of scope for v1. The user said not to worry about them.
- G-022 — `scripts/smoke.ts` also drives the real `inbox-hook` process: a held Write denied from the HTTP API, and fail-open against a home with no daemon. That covers the hook↔daemon seam the unit tests can't, and still needs no Claude account.
- G-023 — `scripts/demo.ts` runs the real daemon on a throwaway home, seeds realistic sessions over the hook socket, and serves the built UI, so the whole loop can be checked in a browser with no Claude account. Integration check found the daemon matched only `content="">`, while Vite emits `content="" />`, so the token never got injected. The match is now a regex, with a test.
- G-024 — Releases are versioned (semver in `VERSION`) and published as GitHub Releases carrying one prebuilt tarball: hook, daemon, `session-inbox` CLI, UI and the menu-bar app. A new Mac installs with one `curl … | sh` and needs neither Bun nor Rust. Why: the source install needs two toolchains and a multi-minute Rust build, which is the wrong first five minutes on a second machine.
- G-025 — One exception to G-003: a small POSIX `install.sh` bootstrap (pick the release, download, check the SHA-256, hand over to the compiled CLI). Why: a fresh Mac has `sh` and `curl` but no Bun. Everything after the hand-over is still Bun.
- G-026 — Updates: the daemon decides *when* (checks on a schedule, applies by itself only while nothing is held or in flight) and the `session-inbox update` CLI does the work (download, verify, run the new version's own installer), so the app's button and the terminal command are the same code path. Not Tauri's updater plugin: it replaces only the app bundle, and hook, daemon, UI and app have to move together.
- G-027 — Release artifacts are Apple silicon only; `install.sh` says so on Intel and points at the source install. Why: this Mac has no Rosetta, so an x86_64 build couldn't be run even once, and an untested binary is worse than a clear message.
- G-028 — Update trust is HTTPS to GitHub plus a SHA-256 sidecar per asset. That is integrity, not authenticity beyond the GitHub account that publishes the release. Why: a separate signing key is one more secret to keep and doesn't change who has to be trusted today; revisit together with Developer ID signing and notarization (S-007).
- G-029 — Releases feed the GA channel only. Beta stays a from-checkout install and never self-updates. Why: beta exists to compare a working branch against GA (H-014); an updater that replaced it with a release would defeat that.
- G-030 — Feature round, 2026-11-09. Five candidates, three kept:
  1. **Settings pane, applied live** (kept). Settings were SQLite rows plus a daemon restart; on a second machine nobody should need `sqlite3` to turn holds off or pick which tools are held.
  2. **Approval preview** (kept): a real diff for Edit/Write/MultiEdit, the full command and working directory for Bash, and what Claude said just before asking. The product's promise is deciding without switching to Claude; a one-line summary isn't enough to decide on.
  3. **Setup check** (kept): `session-inbox doctor` and the same checks in the app (daemon, hooks, holder/observer, `claude` on PATH and logged in, notification delivery). Every item in the "not yet verified" list was an install-environment fact; a second machine will have its own.
  4. **Phone push relay** (cut). Most tempting, since approvals are most useful when you're away from the desk. But it sends prompts, commands and file paths to a third-party service, needs an account and a secret, and breaks G-001 (this Mac only). It needs its own threat model, not a late addition.
  5. **History and search** over finished items and sessions (cut). The snapshot is deliberately a 24-hour working set (D-025) and v1 is an inbox, not a transcript viewer; search adds an index, a query API and a new view for something Claude's own session list already does.
- G-031 — Delegation for this round: Opus 5.5 (medium) for the release/installer CLI, the updater, settings and the approval preview; Sonnet 5.5 (medium) for finishing the beta shell. User instruction: Opus on medium wherever possible, Sonnet never above high.

## Contracts

- C-001 — `packages/contracts` exports Effect Schemas only; it is the only code the daemon and UI share. Node-only helpers (`paths`) live at the `@session-inbox/contracts/paths` subpath so the UI bundle never pulls `node:os`.
- C-002 — Effect 4 dropped `onExcessProperty: "preserve"`. `decodeHookPayload(schema, raw)` decodes and then overlays typed fields onto the raw object, so unknown fields survive. The raw JSON is also stored verbatim in `events.payload_json`.
- C-003 — Added hook events beyond the doc's table: `UserPromptSubmit` (first prompt → provisional title; any prompt confirms an answered item and marks the session running), `SubagentStart` (tree node appears before it finishes), `SessionEnd` (state `ended`; abnormal end → failed). They are cheap and fill gaps the doc left open.
- C-004 — The hook sends an envelope `{event, payload, env, sentAt}`. `env` carries what only the hook's process can see: `CLAUDE_CODE_ENTRYPOINT` (`claude-desktop` ⇒ runtime `desktop`, `cli` ⇒ `cli`), `CLAUDE_CODE_HOST_SESSION_ID` (desktop's `local_<uuid>`, used for deep links), and the parent Claude pid.
- C-005 — Stream messages are a tagged union `hello | delta | notify | badge | reset`. `delta` carries full upserted rows (projects, sessions, agents, items) plus counts, not patches. Simpler to merge, small enough at this scale.
- C-006 — Items carry a daemon-computed `queue` (`needs-you | review | snoozed | done`), `live` (a PreToolUse hook is being held for it right now) and `unconfirmed`. The UI filters on `queue` and never derives it.
- C-007 — Decisions include `ask`, which releases a held hook so Claude's own prompt appears. "Open in Claude" on a live item sends `ask` first, so you're never looking at a frozen session.
- C-008 — Daemon files live in `~/Library/Application Support/SessionInbox/` (override with `SESSION_INBOX_HOME` for tests and dev). Keep test homes short: macOS caps Unix socket paths at 104 bytes.
- C-009 — `hook.ts` gains optional payload fields from the spike (P-002): `prompt_id`, `agent_id`, `agent_type` on `HookBase`; `duration_ms` on PostToolUse; `session_title` on SessionStart; `last_assistant_message`, `background_tasks`, `session_crons` on Stop and SubagentStop. Additive only; all optional because they are absent on some events/versions.
- C-010 — `Item.questionCount` (optional number): set by the daemon on question items that have question rows (AskUserQuestion), absent otherwise (an idle "waiting for input" question has none). Lets cards say "2 questions" without fetching detail. Additive.
- C-011 — `TimelineEntry.isSource` (optional boolean) rather than `ItemDetail.sourceSeq`: the daemon already decides which event made the item and must also inject that event into the timeline when it isn't an activity line, so flagging the entry keeps the UI a plain renderer. Additive.
- C-012 — `Health` and `Connection` gain optional `channel` and `build` so tools and the shell can tell two installs apart. Additive.
- C-013 — `UpdateStatus` and routes `GET /v1/update`, `POST /v1/update/check`, `POST /v1/update/apply` (`{version?}`). Status changes reach pages as a new tagged stream message `update` (live-only like `notify`, no SSE id, sent to every client after `hello` and on each change; not sent when `unsupported`). Old pages decode with `decodeUnknownOption` and skip unknown tags; the shell ignores them too.
- C-014 — `hello` gains optional `version` and `build`, so a page can tell which daemon build it is talking to (U-022). Additive.
- C-016 — Settings pane API: `GET /v1/settings` → `SettingsResponse { settings, defaults, channel, otherChannel }`; `PUT` takes `UserSettingsPatch` (any subset of `UserSettings`, `null` = reset) and answers the same shape. `UserSettings` holds only the user-facing dotted keys; internal ones (`questions.*`, `items.*`, `outbox.*`) stay out of the API. `HOLDABLE_TOOLS` and `SETTING_LIMITS` live in contracts so UI and daemon agree on choices and ranges. Additive.
- C-019 — `Approval` gains optional `preview` (tagged union `diff | command | fetch | generic`; diff = `path, displayPath, isNewFile, approximate, binary, hunks[{oldStart, oldLines, newStart, newLines, lines[{kind, text, noEol?}]}], added, removed, truncated`) and optional `context` (Claude's last text). On `Approval`, not `ItemDetail`, because it belongs to the hold and is stored with it. Additive (G-030 #2).
- C-020 — No new `Item` field for diff stats: the daemon writes them into the permission `summary` ("Wants to edit src/a.ts +12 −3", "Wants to create …"), which cards, compact rows and notifications already show. Cheapest path that keeps the UI a renderer.
- C-021 — Setup check: `GET /v1/doctor` returns a `DoctorReport` (`checks[]` of `{id, title, status: ok|warn|fail|info, detail, fix?}`, plus `ok`, `attention`, `firstRun`); `POST /v1/doctor/notify` sends a test notification down the normal path; a live-only `doctor` stream message tells pages to refetch. The daemon writes every word, so the app and `session-inbox doctor` print the same thing (G-002, G-030 #3).
- C-022 — `POST /v1/shell/status` (`ShellStatus`: the app's notification permission, alert style, version, channel) and a live-only `unnotify {ids}` stream message to shell clients. The daemon owns notification policy but only the app can see its own permission; found live that a denied app swallowed every notification (P-014).
- C-023 — `ItemDetail` gains optional `lastMessage` (what Claude said last, in full, for review and failed items) and `replyUnavailable` (why a free-text reply can't be sent from here). A review item that only shows a one-line summary isn't reviewable, and a reply box that silently fails without a CLI login is worse than none. Additive.
- C-024 — `UserSettings` gains `storage.retentionDays` (number, `SETTING_LIMITS` 1–365, default 14) so the Settings pane can show retention (D-063). A required key, so `FAKE_SETTING_DEFAULTS` in the UI's fake client got the one line it needs to typecheck.

## Daemon

- D-001 — HTTP is `Bun.serve`, not `@effect/platform-bun`'s HttpServer. One plain `fetch` handler per listener serves the hook routes on the Unix socket and the UI routes on TCP, SSE is a `ReadableStream`, and long-polls need per-request idle-timeout control; the Effect server is a single `HttpServer` service per layer and its SSE/long-poll story would have been more code for no gain. `@effect/platform-bun` is still used for `BunRuntime.runMain` (signals, graceful shutdown).
- D-002 — SQLite is `bun:sqlite` directly, not `@effect/sql-sqlite-bun`. The daemon is the single writer and every domain step (ingest, intent, timer) is one synchronous transaction that appends an event, so state, seq and deltas can never interleave; the Effect SQL client is async and would add fiber interleaving inside steps. Effect is used for Schema decoding, `Result`-returning transitions, services/layers (Clock, Git, ClaudeCli, Notifier, Opener, Logger) and timer fibers.
- D-003 — Migrations are numbered `.sql` files imported as text (`with { type: "text" }`) so `bun build --compile` embeds them; applied in order against `PRAGMA user_version`. Pragmas: WAL, foreign_keys, busy_timeout 5000, synchronous NORMAL.
- D-004 — Schema additions over the doc: sessions `title_source`, `host_session_id`, `permission_mode`, `created_at`; items `unread`, `unconfirmed`, `answered_at`, `answered_seq`; questions `header`; approvals `tool_use_id`, `reason`, `updated_input_json`, `live`; outbox `next_attempt_at`, `delivered_at`; notifications `title`, `body`, `actions_json`, `critical`, `channel`, `created_at`; events `env_json`, `decode_error`; new `intents` table for idempotency of mutations that have no outbox row. `approvals.live` is the hold flag (no separate hold table).
- D-005 — Every state change appends an event (hook events by name, daemon changes as `daemon:<what>`: decision, answers, reply, snooze, dismiss, read, open, wake, hold-expired, unconfirmed, title, outbox-*, mute, notification-acted). Exception: draft autosaves (not domain state, fire every ~500 ms) write no event and emit no delta.
- D-006 — Lifecycle events: Refresh, Snooze, Wake, Answer, Confirm, MarkUnconfirmed, Supersede, Expire, Dismiss. Terminal states accept nothing; Expire is legal only for permission items; Dismiss is legal from open/snoozed/answered; `ask` from the user (open/dismiss) counts as Answer. Illegal transitions are logged and ignored, never thrown at a hook.
- D-007 — Dedupe key = `session|agent|kind`, except permission holds add the `tool_use_id`: parallel tool calls in one turn must be separately decidable. A non-held permission from a Notification uses `…|permission|prompt`.
- D-008 — Confirmation: any hook event except Notification confirms the session's answered items whose answer seq is older, unless the item still has a `queued` outbox row (a `sending` row may confirm: the `--resume -p` turn's own SessionStart/UserPromptSubmit is the proof it landed, P-005). The 5-minute unconfirmed window restarts at outbox delivery.
- D-009 — Supersede: activity events (UserPromptSubmit, Pre/PostToolUse, SubagentStart/Stop) resolve the session's open/snoozed non-live review, question and permission items; failed items only on UserPromptSubmit (the user engaged again). Notification and SessionEnd don't supersede, so the idle prompt after a Stop doesn't kill its review item.
- D-010 — Notification hook (P-003): `permission_prompt`/`worker_permission_prompt` → a non-held permission item (actions: open only), skipped if the session already has a permission item open or touched in the last 30 s (our own hold or its lapse); `idle_prompt`/`agent_needs_input` → a question item only if the session has no open item; everything else, unknown included, is timeline-only.
- D-011 — Failed = Stop whose `last_assistant_message` starts with "API Error" or whose transcript tail (last 64 KB) has a last assistant entry with `isApiErrorMessage: true` or an `error` field; or SessionEnd with a reason outside {clear, logout, prompt_input_exit, other, resume, compact}. The review/failed summary is the first line of `last_assistant_message`.
- D-012 — Hold rule (G-014): AskUserQuestion always (unless muted); otherwise tool in `holds.tools`, `permission_mode` missing or `default`, not a deny/allow rule match in user/project/local settings (deny wins, as in Claude), and not a plain read-only Bash command in `holds.safeBashPrefixes` (no shell metacharacters). Settings dirs checked: project root, session worktree, cwd. TODO-SPIKE: the safe-prefix list mirrors Claude's auto-allowed commands only approximately.
- D-013 — Rule matching supports `Tool`, `Tool(exact)`, `Tool(prefix:*)`, `Tool(prefix*)`/`(dir/**)` and `WebFetch(domain:host)`; full gitignore-style globs are not interpreted (a non-match only means we hold when Claude may not have asked; the hold falls back to `ask`).
- D-014 — Allow-always writes to the session's worktree (else the project root) `.claude/settings.local.json`, atomically (tmp + rename), preserving every other key; a file that isn't a JSON object is left alone and the decision still goes through as allow.
- D-015 — Answer encoding lives only in `encodeLiveAnswers`. Mode is `questions.answerMode` (default `updatedInput`) with a per-runtime override `questions.answerModeByRuntime`, written to the settings table automatically when a PostToolUse(AskUserQuestion) `tool_response.answers` doesn't match what we sent (P-004); that item is flagged unconfirmed instead of resolved.
- D-016 — A reply to a live (held) item is not queued: it releases the hook as `deny` with `The user replied: <text>` as the reason. Sending `--resume -p` into a session we are holding would collide with its own turn. The outbox sender also refuses sessions that are `running` or have any live hold.
- D-017 — Outbox: one in-flight send per session; attempts 3, backoff 5 s × 2^(n-1); `sending` rows go back to `queued` on startup. `claude --resume <id> -p` runs in the session cwd with the normal environment (so its hooks are ingested and confirm the reply). The binary can be overridden with `SESSION_INBOX_CLAUDE` (smoke test uses `/usr/bin/false`).
- D-018 — Review notifications are trailing-grouped: the first clean Stop opens a 30 s window (`notifications.reviewGroupMs`); at its end one notification goes out for all still-open review items ("N sessions ready to review"). Persisted since D-031.
- D-019 — `notify` messages are live-only and go to shell clients; they are not in the replay ring (a reconnecting shell would repost). A notification is `posted` once pushed to a shell or the osascript fallback; pending ones (fallback off, or osascript failed) are re-sent when a shell connects, if their item is still open and they're under an hour old. Decisions/dismiss mark the item's notifications `cleared`.
- D-020 — Stream: ring of the last 1000 delta/badge messages; `since` below the ring floor or above the current seq ⇒ `reset`. SSE `id:` is the seq (notify frames have no id). `Last-Event-ID` is accepted as `since`. Heartbeat `: hb` every 15 s. The stream also accepts `?token=` (EventSource can't set headers); everything else needs the Authorization header.
- D-021 — Host header must be exactly `127.0.0.1:<port>` or `localhost:<port>` on every TCP request (static UI included) before anything else; health is the only unauthenticated API route. Hook routes exist only on the socket.
- D-022 — Sessions: runtime is set at creation and later only upgraded from `unknown` to desktop/cli — never changed by a `--resume -p` (`sdk-cli`) process (P-005); `sdk-cli` maps to `unknown`. Events for a session never seen get one created on the fly (daemon installed mid-session). Git info is cached per cwd and refreshed on SessionStart.
- D-023 — Titles: `session_title` from SessionStart wins if present (source `claude`); else the first prompt (≤60 chars, word-trimmed) immediately, then `claude -p --model haiku --settings '{"disableAllHooks":true}'` with `SESSION_INBOX_INTERNAL=1`, 60 s timeout; failures keep the prompt title.
- D-024 — Open in Claude: `openUrlFor` (P-006) gives `claude://code/continue?session=<local_id>` for desktop, `claude://resume?session=<uuid>` otherwise, `claude://code/new?folder=<cwd>` with no usable id. Anything without an exact desktop id also gets `cd <cwd> && claude --resume <id>` on the clipboard. A live item is released with `ask` first (C-007).
- D-025 — Snapshot = sessions not ended or active in the last 24 h (or with open items), their agents and projects, and items that are open/snoozed/answered or changed in the last 24 h. Timeline = the session's last 50 PostToolUse/Subagent*/UserPromptSubmit/Stop events as one-line text.
- D-026 — Timers: one 1 s tick fiber (hold expiry, snooze wake, unconfirmed sweep, review flush, outbox retry) and a 15 s heartbeat fiber, both `Effect.forkScoped` with `Schedule.spaced`. The engine's `tick()` is synchronous and reads the injected clock, so tests drive time with a fake clock. Recovery is just DB state: live holds stay live until `expires_at` and a restarted hook can re-poll the same request id.
- D-027 — The Unix socket listener runs with `idleTimeout: 0` (Bun's types omit it for unix, the runtime honours it; verified a 13 s long-poll) and the TCP listener too, for SSE.
- D-028 — `--dev` uses port 7357 (unless `--port`), so the UI dev proxy has a stable target; `bun run dev` uses `<repo>/.dev/home`. Default UI dir is `<repo>/apps/desktop/dist` relative to the source tree; the compiled binary should be given `SESSION_INBOX_UI_DIR` or `--ui-dir`.
- D-029 — Fixture replay: `test/replay.ts` reads `fixtures/synthetic/*.jsonl` and `fixtures/recorded/*.jsonl` (`{event, payload, env}` per line). Synthetic files may add control lines `{"$": "advance"|"tick"|"decide"|"answer"|"snooze"}`; expectations live in `fixtures.test.ts`. Recorded files must replay with zero decode failures and no notifications.
- D-030 — Item detail timeline always includes the item's `source_seq` event (even a PreToolUse/Notification/SessionEnd, which aren't activity lines, or one older than the 50-line window), flagged `isSource` (C-011). Lines: AskUserQuestion → "Asked N questions", other PreToolUse → the permission summary ("Wants to run …"), Notification → its first line. `source_seq` follows a dedupe refresh, so the marker is the latest event that (re)raised the item.
- D-031 — Pending review-notification group is persisted in a `review_group(item_id, added_at)` table (migration 002) instead of memory; the window opened at `MIN(added_at)`. `tick()` flushes it once the window has passed (rows deleted and notification inserted in one transaction), and `recover()` flushes on startup if the window closed while the daemon was down. Supersedes the "in-memory only" part of D-018.
- D-032 — `POST /v1/notifications/:id/acted` with allow/deny decides first and records the notification as acted only if the decision succeeded. Found live: a rejected Allow on a review notification had already marked it acted.
- D-033 — The daemon takes `--channel`/`SESSION_INBOX_CHANNEL` and swaps the served page's `<title>` for the channel's ("Session Inbox Beta"), so side-by-side windows and tabs are distinguishable. Compiled binaries carry a build stamp (`<sha>[-dirty]`, via `bun build --define`) shown in health, connection.json and the startup log; source runs say `dev`.
- D-034 — A Notification permission prompt doesn't open a new item when the session has an open (or 30 s-recent) question item as well as a permission one. Found live: a lapsed AskUserQuestion hold comes back as "Claude needs your permission to use AskUserQuestion" and opened a duplicate permission item next to the still-open question.
- D-035 — Updates: the daemon decides, `<home>/bin/session-inbox` (override `SESSION_INBOX_CLI`) does the work through the `Updater` service: `update --check --json` (30 s timeout, last JSON line parsed defensively) and `update --yes --to <v>` spawned detached (`setsid`, stdin ignored, output appended to `<home>/update.log`) so launchd stopping our process group spares it. No CLI ⇒ `unsupported`: no checks, no UI. Status is in memory plus `update-state.json`.
- D-036 — Checks run 60 s after start and every `updates.checkIntervalMs` (6 h) from the 1 s tick, async and fail-quiet (errors land in `status.error` and the log, never in a hook). `updates.check=false` stops scheduled checks; a manual check still runs. Auto-apply needs `updates.auto`, `source: "release"`, and quiet: no live hold (it would lapse to Claude's own prompt on restart), no outbox row queued/sending, no hook event in 30 s. A source install only shows the update.
- D-037 — Manual apply (`POST /v1/update/apply`) ignores quietness and works for source installs; 409 when nothing is offered or one is running. A version that failed is never auto-applied again, only by hand ("Try again"); a re-check offering it keeps the failure on screen.
- D-038 — While `updating` the daemon watches the state file (changes after the spawn only, so a stale `failed` can't fail a retry): `failed` there, a non-zero CLI exit, or no change for 10 min ⇒ `failed`; a clean exit with us still alive ⇒ `failed` after 60 s. Events: `daemon:update-available` (once per version), `-started`, `-failed`, `daemon:updated`; routine checks append none.
- D-039 — "Updated" is announced once: at startup a state file saying `done` for our `VERSION`, not yet in `<home>/update-memo.json` (`announced`, `lastRun`), appends `daemon:updated {version, from}` and sets `justUpdatedFrom`/`updatedAt`. No native notification: notifications are rows tied to an attention item and shell clicks route to that item, so the UI toasts instead. The memo is a file, not the settings table, to keep it out of the settings API.
- D-045 — Settings apply live (G-030 #1): `PUT /v1/settings` decodes with unknown keys rejected (400), clamps (`holds.budgetMs` 15–120 s, because the hook stops waiting at 120 s, H-003; `notifications.reviewGroupMs` 0–600 s), dedupes tools and prefixes, upserts rows (`null` deletes the row), mutates the engine's running Settings and appends `daemon:settings {changed, reset}`. The engine already reads `this.settings[...]` at each decision, so every exposed key takes effect on the next event; live holds keep their `expires_at`. Reset goes to code defaults + plist defaults (the engine gets them as `settingDefaults`), so an observer install resets to holds off. Test overrides still win at load time.
- D-046 — Turning `holds.enabled` off releases every live hold through `expireHold` (decision `ask`, the same path mute uses, C-007), so no session stays frozen waiting on an inbox that no longer holds. Turning it on affects only new calls.
- D-047 — `otherChannel` is a static check: the other channel's `inbox.db` exists (H-016). The daemon can't cheaply know whether that daemon holds, so the pane shows a caveat, not a verdict. `scripts/channels.ts holds` still writes rows and restarts both daemons.
- D-055 — Preview diffs are our own pure Myers line diff (`domain/diff.ts`, no dependency): common prefix/suffix trimmed first, 3 lines of context, hunks merged when ≤ 6 equal lines apart. Caps: 400 rendered lines, 64 K chars, 1000 chars per line (then `truncated`); past edit distance 1000 or a 20 000-line middle it degrades to one replace hunk. CRLF → LF, an unterminated last line differs from a terminated one (`noEol`), any NUL byte ⇒ `binary`, no hunks. Counts always cover the whole change.
- D-056 — The preview is computed inside the PreToolUse ingest transaction, only when the call is actually held (not observer channels, not AskUserQuestion, not Notification-only items), and stored in `approvals.preview_json`/`context` (migration `003_approval_preview.sql`). It has to be computed then: the file changes the moment the call is allowed. Reads go through a synchronous `Files` service (regular files ≤ 1 MB, else unreadable); any throw ⇒ no preview, the hold proceeds unchanged (fail open). Edit/MultiEdit apply the edits to the LF-normalised file and diff whole files; a missing match or unreadable file falls back to old vs new strings with `approximate: true`. Write diffs disk vs content (`isNewFile` when missing); NotebookEdit diffs the cell source.
- D-057 — Approval context is the last assistant text before the `tool_use` block with the call's `tool_use_id` in the transcript tail (64 KB, the D-011 reader now shared as `readTail`), skipping tool results and stopping at a typed user prompt; whitespace collapsed and cut at a word to ≤ 600 chars.
- D-058 — Previews hold file contents. They live in the local DB and are served only on the token-authenticated 127.0.0.1 API, exactly like `approvals.input_json` (which already carries Write content and Edit strings), so the exposure doesn't change.
- D-059 — Titles from the transcript (P-015): on SessionStart, UserPromptSubmit, Stop and SubagentStop the daemon reads the transcript tail (64 KB, then the head 16 KB) through `Files` for the latest `custom-title` line, else any `*title` type with a string `*itle` field, else `summary`. It becomes the title with source `claude` and a `daemon:title {source:"transcript"}` event when it changed; it beats prompt and Haiku titles, and Haiku is skipped (and never overwrites it) once one exists.
- D-060 — Prompt titles are cleaned: leading `<tag>…</tag>` blocks (an unclosed one swallows the rest) and a leading "Background (from the session that started this one):" paragraph (in favour of what follows `Task:` or the first blank line) are stripped. Nothing readable left ⇒ "Untitled session" with source `placeholder`, which the next real prompt replaces; Haiku gets the cleaned text, never markup.
- D-061 — `ClaudeCli.authStatus()`: `claude auth status` with `SESSION_INBOX_INTERNAL=1`, 10 s timeout, `loggedIn` parsed from its JSON, cached 10 min in the service; `found:false` when the binary isn't on PATH, unknown on any error. The engine keeps the last answer (refreshed every 60 s from the tick, and on each title and doctor request). Known logged out or missing ⇒ no title generation (one INFO per run), and replies/answers that would go through `--resume` are refused with 409 and the `replyUnavailable` text instead of queueing three failing attempts. Live holds still take replies through the hook (D-016).
- D-062 — Notification routing (C-022): no app ⇒ fallback (or pending when `notifications.fallback` is off); app reported `authorized`/`provisional` ⇒ app only; `denied`/`notDetermined` ⇒ fallback only (or pending); reported `unknown`, or connected 10 s without reporting (an older app) ⇒ both; within those first 10 s ⇒ app now, and the fallback follows if the grace ends, a non-allowed report arrives or the app disconnects first, for notifications still posted on an open item. Status lives in memory, resets when no app is connected, and `daemon:shell-status` is appended only when the reported permission differs from the last recorded one (across reconnects). Pending ones are re-sent when an allowed app connects or reports (D-019).
- D-063 — Retention: `storage.retentionDays` (default 14, 1–365). At startup and then daily from the tick, one transaction deletes finished items (resolved/expired/dismissed, untouched since the cutoff, no queued/sending reply, no live hold) with their questions, approvals, drafts, notifications, review-group and outbox rows; delivered/failed outbox rows, acted/cleared notifications and intents older than the cutoff; events older than the cutoff that no remaining item's `source_seq`/`answered_seq` points at; ended sessions older than the cutoff with no items or outbox rows left, and their agents. One `daemon:pruned` event with counts when anything went. Then `wal_checkpoint(TRUNCATE)` and `incremental_vacuum`; new DB files are created with `auto_vacuum = INCREMENTAL`, and an older file gets one full `VACUUM` (switching it over) only at startup when more than 25 % of it is free pages. Payloads stay raw: retention is the answer to their size.
- D-064 — File paths in timeline lines and in the no-preview permission summary are shown relative to the session's worktree, project root or cwd (the preview's `displayPathFor`), e.g. "Edited src/window.ts".
- D-065 — Setup check (C-021): `Doctor` gathers facts (Claude `settings.json` hooks pointing at `<home>/bin/inbox-hook` via the hook package's own helpers, the binary's executable bit, `<home>/install.json` `source` for the fix command, DB + WAL size) and a pure `buildReport` writes the words. GET is fresh and appends no event; `doctor {attention}` goes to pages whenever the count changes, re-evaluated on shell connect/disconnect/status, the first hook event, a CLI-probe change and every 60 s, and is greeted to each new page. `firstRun` comes from a `meta.firstHookEventAt` settings row (written with the first hook event, or backfilled from events at startup), so pruning can't bring the welcome back. The test notification is item `setup` with no row (`notifications.item_id` is a foreign key); `/acted` on a `setup_…` id is a no-op 200; `daemon:doctor-notify {route, via}` records it.
- D-066 — Approval context is read again when an item is opened, if it was empty at hold time, and only accepted when the call's own `tool_use` block is in the transcript tail. Found live: the PreToolUse hook fires before Claude has written its message to the transcript, so the first read came back empty on a real desktop session. The context doesn't depend on the file's state, unlike the diff, so a later read is safe; it is cached on the approval row without an event (presentation data, like drafts).

## Hook & Ops

- H-001 — `inbox-hook` imports only `contracts/paths` (no Effect, no schema decode) and posts the raw envelope. Why: cold start. The daemon validates; the hook must never be a reason Claude is slow.
- H-002 — Fail open everywhere: any throw, refused/missing socket, 500 ms ingest timeout, non-2xx, or bad stdin JSON → exit 0, empty stdout. Never exit 2. A vanished daemon mid-poll is also silent (not `ask`), so Claude behaves as with no hooks. Only a lapsed hold budget prints `ask`.
- H-003 — Hold budget 120 s (env `SESSION_INBOX_HOLD_SECONDS` overrides, for tests), polled in `wait<=110` slices; a `pending` reply just loops. The registered PreToolUse `timeout` is 130 s so Claude never kills the hook before our own `ask` fallback prints.
- H-004 — No top-level `await` in `main.ts` (the `main()` wrapper): `bun build --bytecode` emits CommonJS and fails otherwise. Compile flags: `--minify --bytecode` for the hook; the daemon uses `--minify` only.
- H-005 — Cold start of the compiled binary (90 MB, daemon down, Apple silicon, Bun 1.4.4): about 30-40 ms steady state. The first exec of a freshly written binary costs about 700 ms (one-off macOS scan). `install.ts` runs `inbox-hook warmup` (with `SESSION_INBOX_INTERNAL=1`, so a no-op) right after copying so Claude's first hook doesn't pay it; the compiled-binary test does the same.
- H-006 — Hook registration format (Claude Code 2.1.x): `hooks.<Event> = [{matcher?, hooks:[{type:"command", command, timeout}]}]`, timeout in seconds, command `"<home>/bin/inbox-hook" <Event>` quoted because the path contains a space. PreToolUse matcher `Bash|Write|Edit|MultiEdit|NotebookEdit|WebFetch|AskUserQuestion` (broader than G-014's allow-rule filter: the daemon decides whether to hold; a non-held PreToolUse just returns no `requestId`). PostToolUse matcher `*`. Others have no matcher, timeout 5.
- H-007 — Settings merge lives in `apps/hook/src/settings.ts` as pure functions, our entries identified by the executable basename `inbox-hook` (so moving `--home` replaces rather than duplicates). Merge replaces ours in place (order of user hooks untouched), removes strays elsewhere, and keeps every other key/hook. `unmergeHooks` removes only groups that became empty because of us, so merge→unmerge round-trips to the original (an originally absent `hooks` key is dropped again). `ops/claude-settings.snippet.json` is generated from `buildHooks("<home>")` and a test keeps it in sync.
- H-008 — `install.ts`/`uninstall.ts` are dry-run by default and print a unified diff of settings.json; `--yes` backs up to `settings.json.bak-<timestamp>` first. A settings file that isn't valid JSON aborts untouched. Scripts import `paths.ts` by relative path (root has no dep on contracts).
- H-009 — launchd plist template sets `SESSION_INBOX_HOME` in `EnvironmentVariables` so a non-default `--home` reaches the daemon; install does `bootout` (ignored), `bootstrap gui/$UID`, `kickstart -k`. Uninstall boots out and removes the plist but leaves binaries and data.
- H-010 — Record mode stores only `{event, payload, env}` with the three env fields the envelope already carries (entrypoint, host session id, claude pid) — never process env, tokens or account ids. Payloads themselves may contain prompts and file contents, so `fixtures/` should be treated as private and scrubbed before anything is committed.
- H-011 — Tests run the hook as a subprocess against a fake daemon on a Unix socket under `/tmp/sih-XXXX`, for both `bun src/main.ts` and a freshly compiled binary. The install-script test runs `--yes` only with `--settings <tmp> --home <tmp> --no-launchd`.
- H-012 — The installer ships the built UI to `<home>/ui`, and the plist sets `SESSION_INBOX_UI_DIR` to it. The compiled daemon can't locate the repo, so without this it served only the placeholder page.
- H-013 — The plist sets PATH to the directory of `claude` (resolved at install time) plus Homebrew and the system dirs. launchd's default PATH has no `~/.local/bin`, so outbox replies and title generation would fail with "claude not found".
- H-014 — Two install channels, GA and beta, live side by side: GA is the everyday install from `main`; beta is installed from a working checkout with `install.ts --channel beta`. Each has its own home (`SessionInbox` / `SessionInbox-beta`), launchd label (`…inboxd` / `…inboxd.beta`), random port and menu-bar app. Both hook into `~/.claude/settings.json`, so both see every session; merge/unmerge take a `keep` list of the other channel's home and never touch its commands (a moved home of the same channel is still replaced).
- H-015 — The installed hook finds its daemon from its own path (`<home>/bin/inbox-hook` → `<home>`) when `SESSION_INBOX_HOME` is unset. Claude doesn't pass our env to hooks, so before this any `--home` install silently talked to the default home.
- H-016 — Only one channel holds hooks. Two daemons holding the same PreToolUse would each wait for their own answer. A channel installed while the other's hooks are present becomes an observer: plist `SESSION_INBOX_SETTINGS` defaults `holds.enabled=false` (settings rows still win). The observer still notifies, so both apps can be compared (the user chose "both notify"). `install.ts --holds` overrides; `scripts/channels.ts holds <ga|beta>` flips both by writing rows and restarting the daemons. An observer opens the same question and permission items the holder does, just not live (its permission notifications offer only Open), so the two inboxes match while the holder waits for you.
- H-017 — `install.ts --app` builds the channel's menu-bar app and installs it into `~/Applications/<title>.app` (user-owned, so no sudo, and a stable path for the login item), quitting a running copy first. `scripts/channels.ts` prints status for both channels (launchd, hooks, holds, build, app, counts, URL).
- H-018 — The installer waits for `launchctl bootout` to finish (polling `launchctl print`) and retries `bootstrap` before giving up, and no longer kickstarts afterwards (RunAtLoad starts it). Found on the real reinstall: an immediate bootstrap failed with exit 5 and left the agent unloaded.
- H-019 — `apps/cli` (`session-inbox`, compiled with `--minify`) holds all install, uninstall, update and status logic; `scripts/install.ts`, `uninstall.ts` and `channels.ts` only build a payload from the checkout and call the same functions. One install path, so a source install and a release install can't drift. The version is the root `VERSION` file, compiled in with `--define SESSION_INBOX_VERSION` (so `release.ts --version` can build a "newer" release for tests); source runs read the file via `@session-inbox/contracts/version`. `inbox-hook --version` and `session-inbox --version` print it; the daemon reports it in `/v1/health`.
- H-020 — Payload layout: `manifest.json` (`{name, version, build, arch:"arm64", builtAt}`), `bin/{inbox-hook,inboxd,session-inbox}`, `ui/`, optional `app/<Title>.app`. A release tarball is `session-inbox-<v>-macos-arm64.tar.gz` with top-level dir `session-inbox-<v>/` plus a `.sha256` sidecar (hex digest + newline). `session-inbox install` without `--from` uses the payload its own binary sits in. The release CLI installs the app by default (`--no-app` skips); the source script still needs `--app`.
- H-021 — Binaries are installed by copying to a temp file beside the target and renaming over it; the UI and app dirs are copied beside and swapped with two renames. Claude runs `inbox-hook` constantly, so its path must never be missing or half-written; a running process keeps its old inode.
- H-022 — `<home>/install.json` records `{version, build, channel, source, home, settingsPath, launchd, hooks, app, appPath, installedAt}`; `update` re-runs the new installer with exactly those choices. `home` is stored as given because the binary's own path can come back as a realpath (`/private/tmp` for `/tmp`), which would otherwise move the hook commands on update (found by the update test).
- H-023 — Update contract for the daemon: run `"<home>/bin/session-inbox" update --yes --to <version>` (stdio ignored). It re-executes itself with `detached: true` (new session and process group), so launchd stopping the daemon's job can't kill it; SIGHUP/SIGPIPE are ignored and stdout is best effort. Progress goes to `<home>/update-state.json` (`{version, state: downloading|verifying|installing|done|failed, error, at}`, written by atomic rename) and `<home>/update.log`. Exit 0 done or already up to date, 1 failed, 2 refused (beta, bad flags). One updater per home (`updates/.lock` with a pid); `updates/` is emptied after success. `update --check --json` prints one JSON line and always exits 0.
- H-024 — During an update the app is quit, replaced and reopened only if it was running; a plain install always opens it. `~/.local/bin/session-inbox` (beta: `session-inbox-beta`) is linked only for the channel's default home, never with sudo, and only replaces a symlink, not a file; a custom `--home` (every test) never touches it.
- H-025 — `scripts/release.ts` builds hook, daemon, CLI, UI and (unless `--skip-app`) the GA app via `build-shell.ts`, then tars with `/usr/bin/tar` and `COPYFILE_DISABLE=1` (no AppleDouble files). `--publish` refuses a dirty tree or an existing tag. The Release workflow (workflow_dispatch, patch/minor/major) bumps `VERSION` with `scripts/bump.ts`, commits, runs every check, builds, tags, pushes and runs `gh release create` itself; CI runs the same checks on push and PR on `macos-latest` (arm64) with Bun 1.4.4.
- H-026 — `install.sh` (G-025) needs only `/usr/bin:/bin:/usr/sbin:/sbin`: `uname`/`sysctl hw.optional.arm64` (so a Rosetta shell still counts as Apple silicon), `curl`, `shasum -a 256`, `tar`. It writes only to a `mktemp -d` dir until it runs the payload's `session-inbox install --from <payload> --yes "$@"`, never reads stdin, and removes the temp dir afterwards (it runs the installer rather than `exec`ing it so the trap can clean up). `SESSION_INBOX_RELEASES_URL` replaces `https://api.github.com/repos/<repo>/releases` in both install.sh and the CLI; `SESSION_INBOX_ASSET_URL` replaces install.sh's download base.
- H-027 — Install from a mirror: `--releases-url`/`--asset-url`/`--repo` (or the same `SESSION_INBOX_*` variables at install time; install.sh passes the ones that are set) are recorded in `install.json` and written into the plist's `EnvironmentVariables`, so the daemon's checks, the detached `update` and every re-install use one source. `update` takes them from the environment when any is set (all three, not mixed key by key), else from `install.json`. Why: under launchd the daemon had no way to be pointed anywhere but GitHub, which made the update path untestable without publishing.
- H-028 — `SESSION_INBOX_ASSET_URL` is a download base in the CLI too: `<base>/<asset name>`, with `{tag}` and `{version}` filled in. A flat mirror needs neither (asset names carry the version); a tag-specific base without `{tag}` still works for install.sh but would break later updates once recorded, so the README shows the `{tag}` form.
- H-029 — `--label <reverse.dns>` on install/uninstall/status/doctor, recorded in `install.json` and passed on by `update`. A non-default label never links `~/.local/bin` and never installs the app into `~/Applications` (both are per channel, not per label). Why: an isolated real-launchd install for the update e2e, and for anyone who wants a third instance.
- H-030 — `--daemon-env KEY=VALUE` (repeatable, undocumented for users) adds plist environment and is kept across updates. The e2e uses it for an empty `CLAUDE_CONFIG_DIR` and `SESSION_INBOX_CLAUDE=/usr/bin/false`, so the e2e daemon reads no real allow rules and never spawns the real `claude`.
- H-031 — `scripts/e2e-update.ts` proves the update path with no GitHub: two `--skip-app` releases from `release.ts`, the shared fake server (`scripts/fake-releases.ts`, also used by `release.test.ts`), an install under the real launchd as `com.sessioninbox.inboxd.e2e` in `/tmp/si-e2e-*`, a live hold through the real `inbox-hook`, the daemon's own auto-apply, a corrupted release and a purge uninstall, and a closing check that the real settings and GA/beta plists didn't change. It stays a script (about a minute, real launchd), not part of `bun test`. It passed on its first full run: the detached updater survives launchd restarting the job, the new port is published, no lock is left.
- H-032 — `session-inbox doctor [--json]` renders the daemon's `GET /v1/doctor` (C-021) as aligned text (✓ ! ✗ ·, details wrapped at 80 columns, fixes as `→ run:` / `→ open:`) and exits 0 only when the report is `ok`. With no `connection.json` or no answer in 3 s it runs its own checks (home, binaries, launchd job, daemon, hooks in the settings file, last 10 log lines) in the same `DoctorReport` shape, so `--json` has one shape; a 404 means the daemon predates the setup check and says so.
- H-033 — The installer clears `com.apple.quarantine` (`/usr/bin/xattr -dr`, errors ignored) on what it copies into `<home>` and `~/Applications`. Why: a tarball downloaded with a browser instead of `curl` carries the flag and Gatekeeper would refuse the ad-hoc-signed binaries and app.
- H-034 — User-facing CLI and installer text never cites decision ids; it says the reason in plain words (comments may keep them). A release install (not an update) ends with what happens next: menu bar, allow notifications, restart open sessions, `doctor`, how to uninstall.
- H-035 — CI has a `package` job: the full `release.ts` (app included) and `scripts/verify-release.ts --require-app`, which checks the checksum, unpacks the tarball and installs it with `--no-launchd --no-app` into a temp HOME, then asks each binary its version. `release.yml` runs the same verification before tagging. Nothing is uploaded from CI.

- U-001 — Set up `apps/desktop` by hand, using `create-foldkit-app@0.41.0` output (ui-showcase, websocket-chat) only as reference. The scaffold pins effect 4.1.0, TypeScript 7, Vitest and oxlint; we need effect 4.1.2 / TS 5.9.3 / `bun test` / Biome (G-005, G-006).

Reconnects resume from the latest merged `seq` with backoff 0.5 s → 15 s; a clean server close also reconnects. `reset` refetches the snapshot; the new snapshot bumps a `streamEpoch` that restarts the stream from its seq.

- U-006 — Basecoat CSS only (`basecoat-css/nova`), never its JS. - U-008 — System font stack (SF on macOS) at 13 px base, not the mockup's Inter: native feel in a menu-bar app and no web-font fetch from a 127.0.0.1 page.
- U-009 — The Model never derives lifecycle/queue/priority: tabs filter on `item.queue`, "Working" lists sessions whose daemon `state` is `running`, counts are `snapshot.counts` verbatim. Optimistic UI is limited to `submission: Sending` (disables buttons); the item itself changes only via the action response or a delta.
- U-010 — Stable list order: the queue shows items in the daemon's snapshot order; ids first seen in a delta are appended (never inserted), so a new item never moves what you're looking at. A fresh snapshot (startup/reset) re-adopts daemon order.
- U-011 — Routing without Foldkit's router: initial `#/item/<id>` arrives as a flag, later changes via a `hashchange` subscription (the shell navigates the hash). Selecting in the UI writes the hash with `history.replaceState` (no history spam, no hashchange loop). `?view=compact` is read once at boot.

- U-013 — ⌘K / ⌘↵ / ⌘⌫ via `Dom.streamFromKeyBindings`. ⌘↵ is "primary action of the detail pane" (send answers → allow once → send reply); ⌘⌫ only denies when a permission is shown and is suppressed while typing so it still deletes text in fields.
- U-014 — Form state per item: one `AnswerDraft {selected, other}` per question; single-choice uses `@foldkit/ui` RadioGroup (one submodel per question), multi-choice uses Checkbox; typing an "other" answer clears a single-choice pick. Drafts are PUT 500 ms after the last edit (versioned debounce); on load the daemon draft (`{answers, reply}`) wins over recorded answers. A detail refetch for the same item keeps in-progress input.
- U-015 — Idempotency keys are `crypto.randomUUID()` generated inside each Command's `execute` (one per user intent), per Foldkit's rule that randomness lives in Commands.
- U-016 — `@foldkit/ui` used: RadioGroup, Checkbox, Textarea, Menu (snooze/dismiss/mute), Dialog + Combobox (⌘K jump), Toast. Not used: VirtualList (queues are tens of items; variable-height cards; not worth the experimental surface) and Query (a plain Command + `DaemonClient` is the adapter). - U-017 — Toasts only for delivery-related confirmations: action accepted (answers/reply/decision/snooze), outbox entries that turn delivered/failed between two detail loads, "Opened in Claude"/"resume command copied" (`url: null`, G-013), and daemon errors. Native alerts stay with the shell (G-012).
- U-018 — The session tree is a flat ARIA tree (`role=tree`, treeitems with `aria-level`, roving tabindex) rather than nested groups: one keydown handler per row, simple focus math, same visual indentation.
- U-019 — A delta that touches the selected item (or its session) refetches `/v1/items/:id`, since deltas carry rows but not detail (outbox, timeline, approval).
- U-020 — ⌘K jump: the combobox is re-initialised (closed, empty, nothing active) each time the dialog opens and whenever the dialog reports `Closed`. Dismissing the dialog with its list showing used to leave the combobox open with the old highlight, so the next ArrowDown moved on from that row instead of landing on the first result. ## Shell

- S-001 — Windows load the daemon's external URL (`http://127.0.0.1:<httpPort>/`, popover `/?view=compact`); no bundled UI, no IPC, no token passing. `frontendDist` is a placeholder page in `src-tauri/offline/`, so the Rust build never depends on the UI. The shell re-reads `connection.json` every 5 s (health loop) and re-navigates any window whose origin no longer matches, so a daemon restart on a new port recovers on its own (verified against the fake daemon).
- S-002 — No capabilities file: the shell only uses Rust-side APIs, so the remote pages get zero Tauri IPC permissions.
- S-003 — Notifications use `mac-notification-sys` 0.6.15 directly (what `tauri-plugin-notification` wraps via notify-rust), not the plugin: the plugin exposes no click/action callbacks on macOS, while mac-notification-sys blocks per notification until click/action/dismiss, so each notification gets its own thread. One action = `SingleAction`; several = a dropdown on the main button (macOS shows one main button). `click`/`open`/`answer` POST acted, then show the main window at `#/item/<itemId>`; `allow`/`deny` POST acted and open nothing. `Info.plist` sets `NSUserNotificationAlertStyle=alert` (legacy notifications need it to show buttons). Unverified: visual delivery and real clicks (no GUI session during the build; `sample` showed the library polling `deliveredNotifications`, so a notification reached usernoted). Needs a human check on a real desktop; NSUserNotification is deprecated and may stop working in a future macOS.
- S-004 — "Pause notifications" is a local toggle that drops non-critical `notify` messages (the daemon still counts them delivered). Critical ones always post.
- S-005 — Dev/test runs (`SESSION_INBOX_HOME` set) never touch launchd or the login item: no `launchctl kickstart`, no autostart registration. In production the shell registers the login item once (marker file in the app data dir, so a user who removes it is not re-enrolled) and kicks the daemon once per offline episode.
- S-006 — Popover hides on blur; a 300 ms guard stops the tray click that caused the blur from re-opening it. Closing the main window hides it; only the tray's Quit exits. Dock icon hidden (Accessory policy).
- S-007 — Bundle is ad-hoc signed (`signingIdentity: "-"`), `--bundles app` only. Enough to run locally; notifications, the login item and deep-link registration may behave differently until a Developer ID signature plus notarization.
- S-008 — The shell's `/v1/stream?client=shell` connection sends no `since`: it only needs live `notify` and `badge`, and a missed badge is corrected by the next one.
- S-009 — Rust is ~450 lines including ~60 of unit tests and comments, over the doc's 300 target: notifications, health, SSE parsing and window plumbing each need a few dozen lines. Split into `main.rs`, `daemon.rs`, `notify.rs`.
- S-010 — The channel is fixed at compile time by `SESSION_INBOX_CHANNEL` (`beta`; anything else is GA), read with `option_env!` in `src/channel.rs`, and `build.rs` reruns on change. Why: GA and beta must differ in identity before any code runs (bundle id, notification app id, URL scheme, launchd label, data home), and a runtime flag could not change the bundle itself.
- S-011 — Beta identity: data home `SessionInbox-beta`, launchd `com.sessioninbox.inboxd.beta`, bundle id `com.sessioninbox.app.beta`, scheme `sessioninbox-beta`, shortcut Cmd+Alt+Shift+I, name "Session Inbox Beta". Why: nothing shared with GA, so both can run and be installed at once (H-014); the shortcut differs because two apps cannot own one global hotkey. The login item name follows the product name, and its marker lives under the identifier-based app data dir, so each channel registers its own.
- S-012 — `build-shell.ts --channel beta` passes `tauri build --config <json>` (version, productName, identifier, deep-link scheme) instead of keeping a second `tauri.conf.json`, and sets the env var for cargo. Each finished bundle is copied (`ditto`, keeps the ad-hoc signature) to `target/release/bundle/<channel>/` and that path is the last stdout line, which `install.ts --app` parses. Why: one config to maintain; the per-channel copy means building one channel never touches the other's bundle, even though both share `target/release`.
- S-013 — The bundle version comes from repo-root `VERSION` when present, else the Cargo package version, and is always passed as the `--config` `version` (so `tauri.conf.json`'s own version is never what ships). Why: `CFBundleShortVersionString` must match the release version without hand-editing three files.
- S-014 — Supersedes S-003: notifications go through `UNUserNotificationCenter` (objc2 0.6.5, objc2-foundation/objc2-user-notifications 0.3.2, block2 0.6.2, the versions tauri/tao already pull, so one objc2 in Cargo.lock); `mac-notification-sys` is gone. Why: on macOS 27 the legacy API never asked for permission, so usernoted held GA at `authorizationStatus: Denied` and showed nothing while the daemon counted it posted, and its per-notification polling logged ~170 `NSKeyedUnarchiver` faults/s. The UN build logs no such faults and idles at 0.0% CPU with notifications outstanding.
- S-015 — The UN delegate is set in Tauri `setup`, which tao runs synchronously inside `applicationDidFinishLaunching` (`launched` → `StartCause::Init` → `RunEvent::Ready` → setup), so a click that cold-starts the app is still delivered. One category per action set (`si.allow-deny-open`, `si.answer-open`, `si.open`, registered up front); Allow/Deny don't foreground, Deny is destructive. Default click → `click`, dismiss ignored; `acted` runs on a thread and the completion handler is called at once. `critical` stays an ordinary alert (time-sensitive needs an entitlement) but bypasses Pause (S-004).
- S-016 — The shell reports `POST /v1/shell/status` `{notifications, alertStyle, version, channel}` after the authorization callback, on every stream (re)connect, and when the 5 s health loop sees the settings change. Errors and 404s are logged, never retried. Why: the daemon owns the osascript fallback (G-018) and needs to know when the shell cannot show anything. Observed on macOS 27: `getNotificationSettings` says `denied` both while the prompt is pending and after it closes unanswered. The prompt is one-shot (it disappears when the app quits, and later launches get `granted=false` straight away), so the tray shows "Notifications are off — Open Settings…" while denied.
- S-017 — `{"_tag":"unnotify","ids":[…]}` removes delivered and pending notifications by id (the request identifier is the daemon's notification id, the thread identifier its item id). Unknown tags are still ignored. Verified in usernoted's log against the fake daemon.
- S-018 — `Info.plist` (`NSUserNotificationAlertStyle=alert`) is dropped. With the key in the beta bundle, usernoted still recorded `alertStyle: Banner` for the UN app, so UN ignores it. Users who want persistent Allow/Deny alerts pick "Alerts" in System Settings.
- S-019 — Startup hardening: a taken global shortcut, failed login-item registration or missing app-data dir are logged and launch continues. Without an `.app` bundle (`cargo run`), notifications are skipped and status is `unknown`, because `UNUserNotificationCenter` raises there. Exec'ing `Contents/MacOS/session-inbox-shell` directly and `open -n -a … --env` both give the bundle identity. The tray adds "<Product> <version>" (disabled) and "Check for Updates…" (main window at `#/update`).
- S-020 — The app asks launchd to start an offline daemon with `launchctl kickstart`, without `-k`. Found on a real reinstall: the app noticed the daemon was away for a moment, and its `kickstart -k` killed the daemon the installer had just started (launchd logged a second run, exit 130). Without `-k` a running job is left alone.
- S-021 — The tray menu gains "Settings…" (`#/settings`) and "Setup Check…" (`#/setup`), grouped with "Check for Updates…"; status and version lines move below them. Why: the three things a person looks for in a menu-bar app's menu were only reachable from inside the window.

## Phase 0 spike findings

- P-001 — Phase 0 had no model access: child `claude -p` runs fail auth inside the agent sandbox. Live-proven: SessionStart/UserPromptSubmit/SessionEnd payloads, `--resume`, worktree `cwd`. Everything else is static (binary/asar) and marked unverified; `scripts/spike/live.ts` runs the rest. Fixtures hold only real payloads. Why: don't build contract tests on invented data.
- P-002 — Hook payload deltas vs `contracts/hook.ts`: add optional `prompt_id` (UserPromptSubmit, SessionEnd, others), `duration_ms` (PostToolUse), `last_assistant_message`, `background_tasks`, `session_crons` (Stop, SubagentStop), `session_title`, `agent_type` (SessionStart). `permission_mode` is absent on SessionStart/SessionEnd, so keep it optional. `cwd` is the realpath. Keep decoding with `decodeHookPayload` so unknown fields survive.
- P-003 — Classify Notification by `notification_type`: `permission_prompt` and `worker_permission_prompt` become approval items; `idle_prompt` ("Claude is waiting for your input") and `agent_needs_input` become "needs you"; `agent_completed` is informational; `elicitation_response`, `elicitation_complete`, `auth_success`, `auth_storage_failure`, `push_notification`, `plugin_notification`, `computer_use_enter`, `computer_use_exit` are ignored for the inbox. Unknown types default to ignored, never to an alert. Why: the CLI's emitted set (static); an unknown type must not spam.
- P-004 — AskUserQuestion answer mode: default **`updatedInput`** (`allow` + `updatedInput = tool_input + answers:{"<question text>":"<option label>"}`; multi-select comma separated), because `call()` reads `input.answers` and the result text is the clean "Your questions have been answered" message. Verify with the PostToolUse for AskUserQuestion: its `tool_response.answers` must equal what was sent; if the answers are empty or the tool still prompted, the daemon switches that session to **`denyWithReason`** (`deny` + reason `The user answered via Session Inbox: <question> → <label>`) and remembers it per runtime. Make the mode a daemon setting (`ask_answer_mode`). Unverified live (see spike.md Q3): `requiresUserInteraction` may stop a hook allow from skipping the card.
- P-005 — `--resume <id> -p` keeps the same `session_id` and appends to the same transcript (live). Its SessionStart arrives with `source:"resume"` and `entrypoint:"sdk-cli"`: never create a new session or change a desktop session's runtime from it. Use it only when the session has no running turn. Concurrent mid-turn resume is untested, so stay conservative. Desktop sessions: acceptable for idle/waiting sessions; prefer the PreToolUse path for live questions (G-015).
- P-006 — "Open in Claude" links: desktop session `claude://code/continue?session=<hostSessionId>` (`local_<uuid>` from `CLAUDE_CODE_HOST_SESSION_ID`); CLI session `claude://resume?session=<session_id>` (imports into desktop) with the copy-`cd … && claude --resume <id>` fallback; project-only fallback `claude://code/new?folder=<cwd>`; unknown id lands on `/epitaxy` (harmless). Needs the desktop app logged in and deep links enabled. Static; test one link after install.
- P-007 — Desktop Code-tab sessions load user-level hooks: the session spawn passes `settingSources:["user","project","local"]` and does not set `disableAllHooks`. Static plus the live evidence of this agent session. Verify live after install with one desktop session and a `local_<uuid>` hostSessionId in the event.
- P-008 — PreToolUse decisions: besides allow/deny/ask there is `defer` (print mode only, ignore it). The hook must answer within its own `timeout` (set it above the daemon hold, default hold 120 s so `timeout: 130`) and answer `ask` itself on expiry rather than relying on timeout semantics, which are unverified (a timed-out hook is expected to fall through, but a "hook did not finish, call not run" path exists for cloud sessions). Desktop registers its own PreToolUse hook (`permissionDisplay`); interaction with ours is unverified.
- P-009 — Worktree payloads carry the worktree path as `cwd` (live). Project grouping must resolve the main worktree via `git rev-parse --git-common-dir` in the daemon (G-019); never group by `cwd` string.
- P-010 — Notification hooks cannot be triggered in `-p`; the first real Notification fixture must come from a desktop/CLI interactive session after install (`inbox-hook record`).
- P-011 — Live: the desktop app logs `Mapping internal session local_<uuid> to CLI session <session_id>`, confirming that a Code-tab session's `CLAUDE_CODE_HOST_SESSION_ID` and its hook `session_id` are two ids for one session. `open "claude://code/continue?session=local_<uuid>"` exits 0 with no error. The app doesn't log deep-link handling, so a person still has to confirm by eye that it lands on the session.
- P-012 — Live (2026-11-09, desktop session, Claude Code 2.1.321): an answer sent from the inbox to a held AskUserQuestion arrived as `allow` + `updatedInput.answers`, and the PostToolUse `tool_response.answers` matched it exactly 27 ms after the decision. `questions.answerModeByRuntime` stayed empty, so `updatedInput` is the right default (closes the P-004 question for desktop).
- P-013 — Live: Allow from the inbox on a held Bash ran the command 0.5 s after the decision. The first Bash of a session ran 10.7 s after the decision, twice, however long the hold had lasted; that is Claude's own first-Bash setup, not the hook (which exits right after printing). Nothing to fix on our side.
- P-014 — Live: the menu-bar app's notifications were never displayed. `usernoted` logs every one as `LEGACY` with `authorizationStatus: Denied, notificationsAllowed: false`, and `com.apple.ncprefs` has no entry for `com.sessioninbox.app`: the deprecated NSUserNotification API no longer asks for permission on macOS 27, so the app sits at Denied while the daemon records "posted" and skips its osascript fallback. - P-015 — Desktop transcripts carry the app's own session title as `{"type":"custom-title","customTitle":"…"}` lines (repeated through the file).
