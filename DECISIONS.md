## General

- G-001 — Scope is **local sessions on this Mac only** (CLI + Claude desktop's Code tab). No cloud sessions, no sync. User answered this in the doc's open questions.
- G-002 — The daemon is the only place that decides (classification, lifecycle, priority, notification policy, dedupe, reply routing). UI and shell render and send intents. Straight from the doc's guiding principle.
- G-003 — Bun is the language and runtime for everything that isn't Rust: daemon, hook, UI build, and all repo tooling (`scripts/*.ts` run with `bun`). No Node, npm, or shell scripts beyond one-liners. User instruction.
- G-004 — One Bun workspace: `apps/{daemon,hook,desktop}`, `packages/contracts`, `ops/`, `scripts/`, `fixtures/`. Matches the doc's repo layout.
- G-005 — Pin exact versions: `effect@4.1.2` (Foldkit 0.170 peers on `effect ~4.1.0`, `@effect/platform-bun` and `@effect/sql-sqlite-bun` are 4.1.2), `foldkit@0.170.0`, `@foldkit/ui@0.170.0`, `basecoat-css@1.1.0`, `tailwindcss@4.3.5`, `@biomejs/biome@2.6.6`, `typescript@5.9.3`. Doc says pin; 4.1.x is the one line all of them agree on.
- G-006 — TypeScript 5.9.3, not 7.x. Foldkit/Effect tooling is tested against 5.x; tsc is only used for `typecheck`, Bun runs TS directly.
- G-007 — Rust installed with Homebrew (`brew install rust`) because Tauri v2 needs cargo and none was present. Homebrew was already the machine's package manager; rustup can replace it later without code changes.
- G-008 — Work happens on short-lived branches per area (worktrees), merged to `main` often. User instruction: commit and merge frequently.
- G-009 — Testing is light and layered: pure unit tests (`bun test`) for domain transitions and UI update functions; fixture replay of real hook JSON against in-memory SQLite; a `scripts/smoke.ts` end-to-end run (daemon + hook binary + fake Claude payloads) that needs no Claude account. User asked for light ways to verify while building.
- G-010 — Delegation: Opus 5.5 (medium) for the daemon and the Foldkit UI (design-heavy, unfamiliar APIs); Sonnet 5.5 (medium) for the hook CLI, ops/install scripts, the Phase 0 spike and the Tauri shell (well-specified, mechanical). User instruction.
- G-011 — The daemon serves the built UI same-origin at `http://127.0.0.1:<port>/` and injects the bearer token into `<meta name="session-inbox-token">` (only after a Host-header check against DNS rebinding). The Tauri windows just load that URL, and so does a plain browser, so the UI needs no Tauri APIs and can be tested in any browser. The UI always calls relative `/v1/...`; in dev a proxy adds the header.
- G-012 — The shell, not the webview, consumes the daemon stream for native work: a Rust SSE client (`?client=shell`) posts notifications and sets the tray badge. Notifications then don't depend on a webview being alive, and the UI stays shell-agnostic.
- G-013 — The daemon itself opens "Open in Claude" URLs (`open <url>`); the shell needs no opener plugin. For CLI sessions with no URL, it copies `cd <cwd> && claude --resume <id>` to the clipboard.
- G-014 — Hold a PreToolUse only when Claude itself would have asked (permission_mode `default`, tool in the hold matcher, no matching allow rule in user/project/local settings, project not muted). AskUserQuestion is always held. Otherwise the inbox would add friction where Claude adds none.
- G-015 — Answering a pending AskUserQuestion goes back through its held PreToolUse hook (`allow` + `updatedInput.answers`, or `deny` + reason as a fallback the spike picks). `--resume -p` is only for idle/waiting sessions (free-text replies, non-live questions).
- G-016 — "Always allow" writes to `<project>/.claude/settings.local.json` `permissions.allow`, the same scope Claude's own "don't ask again for this project" uses. The user answered yes to writing Claude's settings; project scope keeps the blast radius small.
- G-017 — Session titles: the first prompt right away, then a 3–6 word title from `claude -p --model haiku` run with `SESSION_INBOX_INTERNAL=1` and hooks disabled so it's never ingested. The user answered "yes" to both options in the doc, so we do both: instant fallback, better title moments later.
- G-018 — Without a connected shell, the daemon falls back to `osascript` notifications (no actions) so "window closed ⇒ one notification within 2 s" holds even before the Tauri app runs.
- G-019 — Project = the main worktree root (via `git rev-parse --git-common-dir`). A session in a linked worktree records it in `session.worktree`, so all of a repo's worktrees group under one project.
- G-020 — `scripts/install.ts` is a dry run by default. It touches `~/.claude/settings.json` and launchd only with `--yes`, backs up first, and merges idempotently. Installing hooks globally changes every Claude session on the machine, so it's an explicit step.
- G-021 — Quiet hours are out of scope for v1. The user said not to worry about them.
- G-022 — `scripts/smoke.ts` also drives the real `inbox-hook` process: a held Write denied from the HTTP API, and fail-open against a home with no daemon. That covers the hook↔daemon seam the unit tests can't, and still needs no Claude account.
- G-023 — `scripts/demo.ts` runs the real daemon on a throwaway home, seeds realistic sessions over the hook socket, and serves the built UI, so the whole loop can be checked in a browser with no Claude account. Integration check found the daemon matched only `content="">`, while Vite emits `content="" />`, so the token never got injected. The match is now a regex, with a test.

## Contracts

- C-001 — `packages/contracts` exports Effect Schemas only; it is the only code the daemon and UI share. Node-only helpers (`paths`) live at the `@session-inbox/contracts/paths` subpath so the UI bundle never pulls `node:os`.
- C-002 — Effect 4 dropped `onExcessProperty: "preserve"`. `decodeHookPayload(schema, raw)` decodes and then overlays typed fields onto the raw object, so unknown fields survive. The raw JSON is also stored verbatim in `events.payload_json`.
- C-003 — Added hook events beyond the doc's table: `UserPromptSubmit` (first prompt → provisional title; any prompt confirms an answered item and marks the session running), `SubagentStart` (tree node appears before it finishes), `SessionEnd` (state `ended`; abnormal end → failed). They are cheap and fill gaps the doc left open.
- C-004 — The hook sends an envelope `{event, payload, env, sentAt}`. `env` carries what only the hook's process can see: `CLAUDE_CODE_ENTRYPOINT` (`claude-desktop` ⇒ runtime `desktop`, `cli` ⇒ `cli`), `CLAUDE_CODE_HOST_SESSION_ID` (desktop's `local_<uuid>`, used for deep links), and the parent Claude pid.
- C-005 — Stream messages are a tagged union `hello | delta | notify | badge | reset`. `delta` carries full upserted rows (projects, sessions, agents, items) plus counts, not patches. Simpler to merge, small enough at this scale.
- C-006 — Items carry a daemon-computed `queue` (`needs-you | review | snoozed | done`), `live` (a PreToolUse hook is being held for it right now) and `unconfirmed`. The UI filters on `queue` and never derives it.
- C-007 — Decisions include `ask`, which releases a held hook so Claude's own prompt appears. "Open in Claude" on a live item sends `ask` first, so you're never looking at a frozen session.
- C-008 — Daemon files live in `~/Library/Application Support/SessionInbox/` (override with `SESSION_INBOX_HOME` for tests and dev). Keep test homes short: macOS caps Unix socket paths at 104 bytes.
- C-009 — `hook.ts` gains optional payload fields from the spike (P-002): `prompt_id`, `agent_id`, `agent_type` on `HookBase`; `duration_ms` on PostToolUse; `session_title` on SessionStart; `last_assistant_message`, `background_tasks`, `session_crons` on Stop and SubagentStop. Additive only; all optional because they are absent on some events/versions.

## Daemon

- D-001 — HTTP is `Bun.serve`, not `@effect/platform-bun`'s HttpServer. One plain `fetch` handler per listener serves the hook routes on the Unix socket and the UI routes on TCP, SSE is a `ReadableStream`, and long-polls need per-request idle-timeout control; the Effect server is a single `HttpServer` service per layer and its SSE/long-poll story would have been more code for no gain. `@effect/platform-bun` is still used for `BunRuntime.runMain` (signals, graceful shutdown).
- D-002 — SQLite is `bun:sqlite` directly, not `@effect/sql-sqlite-bun`. The daemon is the single writer and every domain step (ingest, intent, timer) is one synchronous transaction that appends an event, so state, seq and deltas can never interleave; the Effect SQL client is async and would add fiber interleaving inside steps. Effect is used for Schema decoding, `Result`-returning transitions, services/layers (Clock, Git, ClaudeCli, Notifier, Opener, Logger) and timer fibers.
- D-003 — Migrations are numbered `.sql` files imported as text (`with { type: "text" }`) so `bun build --compile` embeds them; applied in order against `PRAGMA user_version`. Pragmas: WAL, foreign_keys, busy_timeout 5000, synchronous NORMAL.
- D-004 — Schema additions over the doc: sessions `title_source`, `host_session_id`, `permission_mode`, `created_at`; items `unread`, `unconfirmed`, `answered_at`, `answered_seq`; questions `header`; approvals `tool_use_id`, `reason`, `updated_input_json`, `live`; outbox `next_attempt_at`, `delivered_at`; notifications `title`, `body`, `actions_json`, `critical`, `channel`, `created_at`; events `env_json`, `decode_error`; new `intents` table for idempotency of mutations that have no outbox row. `approvals.live` is the hold flag (no separate hold table).
- D-005 — Every state change appends an event (hook events by name, daemon changes as `daemon:<what>`: decision, answers, reply, snooze, dismiss, read, open, wake, hold-expired, unconfirmed, title, outbox-*, mute, notification-acted). Exception: draft autosaves (not domain state, fire every ~500 ms) write no event and emit no delta.
- D-006 — Lifecycle events: Refresh, Snooze, Wake, Answer, Confirm, MarkUnconfirmed, Supersede, Expire, Dismiss. Terminal states accept nothing; Expire is legal only for permission items; Dismiss is legal from open/snoozed/answered; `ask` from the user (open/dismiss) counts as Answer. Illegal transitions are logged and ignored, never thrown at a hook.
- D-007 — Dedupe key = `session|agent|kind`, except permission holds add the `tool_use_id`: parallel tool calls in one turn must be separately decidable. A non-held permission from a Notification uses `…|permission|prompt`.
- D-008 — Confirmation: any hook event except Notification confirms the session's answered items whose answer seq is older, unless the item still has a `queued` outbox row (a `sending` row may confirm: the `--resume -p` turn's own SessionStart/UserPromptSubmit is the proof it landed, P-005). The 5-minute unconfirmed window restarts at outbox delivery.
- D-009 — Supersede: activity events (UserPromptSubmit, Pre/PostToolUse, SubagentStart/Stop) resolve the session's open/snoozed non-live review, question and permission items; failed items only on UserPromptSubmit (the user engaged again). Notification and SessionEnd don't supersede, so the idle prompt after a Stop doesn't kill its review item.
- D-010 — Notification hook (P-003): `permission_prompt`/`worker_permission_prompt` → a non-held permission item (actions: open only), skipped if the session already has a permission item open or touched in the last 30 s (our own hold or its lapse); `idle_prompt`/`agent_needs_input` → a question item only if the session has no open item; everything else, unknown included, is timeline-only.
- D-011 — Failed = Stop whose `last_assistant_message` starts with "API Error" or whose transcript tail (last 64 KB) has a last assistant entry with `isApiErrorMessage: true` or an `error` field; or SessionEnd with a reason outside {clear, logout, prompt_input_exit, other, resume, compact}. The review/failed summary is the first line of `last_assistant_message`.
- D-012 — Hold rule (G-014): AskUserQuestion always (unless muted); otherwise tool in `holds.tools`, `permission_mode` missing or `default`, not a deny/allow rule match in user/project/local settings (deny wins, as in Claude), and not a plain read-only Bash command in `holds.safeBashPrefixes` (no shell metacharacters). Settings dirs checked: project root, session worktree, cwd. TODO-SPIKE: the safe-prefix list mirrors Claude's auto-allowed commands only approximately.
- D-013 — Rule matching supports `Tool`, `Tool(exact)`, `Tool(prefix:*)`, `Tool(prefix*)`/`(dir/**)` and `WebFetch(domain:host)`; full gitignore-style globs are not interpreted (a non-match only means we hold when Claude may not have asked; the hold falls back to `ask`).
- D-014 — Allow-always writes to the session's worktree (else the project root) `.claude/settings.local.json`, atomically (tmp + rename), preserving every other key; a file that isn't a JSON object is left alone and the decision still goes through as allow.
- D-015 — Answer encoding lives only in `encodeLiveAnswers`. Mode is `questions.answerMode` (default `updatedInput`) with a per-runtime override `questions.answerModeByRuntime`, written to the settings table automatically when a PostToolUse(AskUserQuestion) `tool_response.answers` doesn't match what we sent (P-004); that item is flagged unconfirmed instead of resolved.
- D-016 — A reply to a live (held) item is not queued: it releases the hook as `deny` with `The user replied: <text>` as the reason. Sending `--resume -p` into a session we are holding would collide with its own turn. The outbox sender also refuses sessions that are `running` or have any live hold.
- D-017 — Outbox: one in-flight send per session; attempts 3, backoff 5 s × 2^(n-1); `sending` rows go back to `queued` on startup. `claude --resume <id> -p` runs in the session cwd with the normal environment (so its hooks are ingested and confirm the reply). The binary can be overridden with `SESSION_INBOX_CLAUDE` (smoke test uses `/usr/bin/false`).
- D-018 — Review notifications are trailing-grouped: the first clean Stop opens a 30 s window (`notifications.reviewGroupMs`); at its end one notification goes out for all still-open review items ("N sessions ready to review"). In-memory only; a restart drops a pending group (the items remain).
- D-019 — `notify` messages are live-only and go to shell clients; they are not in the replay ring (a reconnecting shell would repost). A notification is `posted` once pushed to a shell or the osascript fallback; pending ones (fallback off, or osascript failed) are re-sent when a shell connects, if their item is still open and they're under an hour old. Decisions/dismiss mark the item's notifications `cleared`.
- D-020 — Stream: ring of the last 1000 delta/badge messages; `since` below the ring floor or above the current seq ⇒ `reset`. SSE `id:` is the seq (notify frames have no id). `Last-Event-ID` is accepted as `since`. Heartbeat `: hb` every 15 s. The stream also accepts `?token=` (EventSource can't set headers); everything else needs the Authorization header.
- D-021 — Host header must be exactly `127.0.0.1:<port>` or `localhost:<port>` on every TCP request (static UI included) before anything else; health is the only unauthenticated API route. Hook routes exist only on the socket.
- D-022 — Sessions: runtime is set at creation and later only upgraded from `unknown` to desktop/cli — never changed by a `--resume -p` (`sdk-cli`) process (P-005); `sdk-cli` maps to `unknown`. Events for a session never seen get one created on the fly (daemon installed mid-session). Git info is cached per cwd and refreshed on SessionStart.
- D-023 — Titles: `session_title` from SessionStart wins if present (source `claude`); else the first prompt (≤60 chars, word-trimmed) immediately, then `claude -p --model haiku --settings '{"disableAllHooks":true}'` with `SESSION_INBOX_INTERNAL=1`, 60 s timeout; failures keep the prompt title.
- D-024 — Open in Claude: `openUrlFor` (P-006) gives `claude://code/continue?session=<local_id>` for desktop, `claude://resume?session=<uuid>` otherwise, `claude://code/new?folder=<cwd>` with no usable id. Anything without an exact desktop id also gets `cd <cwd> && claude --resume <id>` on the clipboard. A live item is released with `ask` first (C-007).
- D-025 — Snapshot = sessions not ended or active in the last 24 h (or with open items), their agents and projects, and items that are open/snoozed/answered or changed in the last 24 h. Timeline = the session's last 50 PostToolUse/Subagent*/UserPromptSubmit/Stop events as one-line text.
- D-026 — Timers: one 1 s tick fiber (hold expiry, snooze wake, unconfirmed sweep, review flush, outbox retry) and a 15 s heartbeat fiber, both `Effect.forkScoped` with `Schedule.spaced`. The engine's `tick()` is synchronous and reads the injected clock, so tests drive time with a fake clock. Recovery is just DB state: live holds stay live until `expires_at` and a restarted hook can re-poll the same request id.
- D-027 — The Unix socket listener runs with `idleTimeout: 0` (Bun's types omit it for unix, the runtime honours it; verified a 13 s long-poll) and the TCP listener too, for SSE.
- D-028 — `--dev` uses port 7357 (unless `--port`), so the UI dev proxy has a stable target; `bun run dev` uses `<repo>/.dev/home`. Default UI dir is `<repo>/apps/desktop/dist` relative to the source tree; the compiled binary should be given `SESSION_INBOX_UI_DIR` or `--ui-dir`.
- D-029 — Fixture replay: `test/replay.ts` reads `fixtures/synthetic/*.jsonl` and `fixtures/recorded/*.jsonl` (`{event, payload, env}` per line). Synthetic files may add control lines `{"$": "advance"|"tick"|"decide"|"answer"|"snooze"}`; expectations live in `fixtures.test.ts`. Recorded files must replay with zero decode failures and no notifications.

## Hook & Ops

- H-001 — `inbox-hook` imports only `contracts/paths` (no Effect, no schema decode) and posts the raw envelope. Why: cold start. The daemon validates; the hook must never be a reason Claude is slow.
- H-002 — Fail open everywhere: any throw, refused/missing socket, 500 ms ingest timeout, non-2xx, or bad stdin JSON → exit 0, empty stdout. Never exit 2. A vanished daemon mid-poll is also silent (not `ask`), so Claude behaves as with no hooks. Only a lapsed hold budget prints `ask`.
- H-003 — Hold budget 120 s (env `SESSION_INBOX_HOLD_SECONDS` overrides, for tests), polled in `wait<=110` slices; a `pending` reply just loops. The registered PreToolUse `timeout` is 130 s so Claude never kills the hook before our own `ask` fallback prints.
- H-004 — No top-level `await` in `main.ts` (the `main()` wrapper): `bun build --bytecode` emits CommonJS and fails otherwise. Compile flags: `--minify --bytecode` for the hook; the daemon uses `--minify` only.
- H-005 — Cold start of the compiled binary (90 MB, daemon down, Apple silicon, Bun 1.4.4): about 30-40 ms steady state. The first exec of a freshly written binary costs about 700 ms (one-off macOS scan). `install.ts` runs `inbox-hook warmup` (with `SESSION_INBOX_INTERNAL=1`, so a no-op) right after copying so Claude's first hook doesn't pay it; the compiled-binary test does the same.
- H-006 — Hook registration format (Claude Code 2.1.x): `hooks.<Event> = [{matcher?, hooks:[{type:"command", command, timeout}]}]`, timeout in seconds, command `"<home>/bin/inbox-hook" <Event>` quoted because the path contains a space. PreToolUse matcher `Bash|Write|Edit|MultiEdit|NotebookEdit|WebFetch|AskUserQuestion` (broader than G-014's allow-rule filter: the daemon decides whether to hold; a non-held PreToolUse just returns no `requestId`). PostToolUse matcher `*`. Others have no matcher, timeout 5.
- H-007 — Settings merge lives in `apps/hook/src/settings.ts` as pure functions, our entries identified by the executable basename `inbox-hook` (so moving `--home` replaces rather than duplicates). Merge replaces ours in place (order of user hooks untouched), removes strays elsewhere, and keeps every other key/hook. `unmergeHooks` removes only groups that became empty because of us, so merge→unmerge round-trips to the original (an originally absent `hooks` key is dropped again). `ops/claude-settings.snippet.json` is generated from `buildHooks("<home>")` and a test keeps it in sync.
- H-008 — `install.ts`/`uninstall.ts` are dry-run by default and print a unified diff of settings.json; `--yes` backs up to `settings.json.bak-<timestamp>` first. A settings file that isn't valid JSON aborts untouched. Scripts import `paths.ts` by relative path (root has no dep on contracts).
- H-009 — launchd plist template sets `SESSION_INBOX_HOME` in `EnvironmentVariables` so a non-default `--home` reaches the daemon; install does `bootout` (ignored), `bootstrap gui/$UID`, `kickstart -k`. Uninstall boots out and removes the plist but leaves binaries and data.
- H-010 — Record mode stores only `{event, payload, env}` with the three env fields the envelope already carries (entrypoint, host session id, claude pid) — never process env, tokens or account ids. Payloads themselves may contain prompts and file contents, so `fixtures/` should be treated as private and scrubbed before anything is committed.
- H-011 — Tests run the hook as a subprocess against a fake daemon on a Unix socket under `/tmp/sih-XXXX`, for both `bun src/main.ts` and a freshly compiled binary. The install-script test runs `--yes` only with `--settings <tmp> --home <tmp> --no-launchd`.
- H-012 — The installer ships the built UI to `<home>/ui`, and the plist sets `SESSION_INBOX_UI_DIR` to it. The compiled daemon can't locate the repo, so without this it served only the placeholder page.
- H-013 — The plist sets PATH to the directory of `claude` (resolved at install time) plus Homebrew and the system dirs. launchd's default PATH has no `~/.local/bin`, so outbox replies and title generation would fail with "claude not found".

## UI

- U-001 — Set up `apps/desktop` by hand, using `create-foldkit-app@0.41.0` output (ui-showcase, websocket-chat) only as reference. The scaffold pins effect 4.1.0, TypeScript 7, Vitest and oxlint; we need effect 4.1.2 / TS 5.9.3 / `bun test` / Biome (G-005, G-006).
- U-002 — Build and dev server are Vite 8.3.6 run under Bun (`bun --bun vite`) with `@tailwindcss/vite` and `@foldkit/vite-plugin@0.29.0` (view identity + live reload; devtools MCP port disabled). Foldkit's tooling is Vite-based; Bun is still the runtime (G-003).
- U-003 — The stream is read with `fetch` + our own incremental SSE parser (`src/client/sse.ts`, pure, unit-tested on every chunk split), not EventSource, which can't send `Authorization`. Reconnects resume from the latest merged `seq` with backoff 0.5 s → 15 s; a clean server close also reconnects. `reset` refetches the snapshot; the new snapshot bumps a `streamEpoch` that restarts the stream from its seq.
- U-004 — `DaemonClient` is an Effect service (`Context.Service`) provided through Foldkit's `resources` Layer. HTTP impl reads the token from `<meta name="session-inbox-token">` and only calls relative `/v1/...`. A fake impl (`src/client/fake.ts`) plays the daemon (state, queues, counts, deltas, outbox walk, background activity) for `bun run dev:mock`. Choice: build-time `SESSION_INBOX_CLIENT=fake`, overridable at runtime with `?client=fake|http`; the fake is a lazy chunk so the HTTP build doesn't load it.
- U-005 — Dev proxy: Vite proxies `/v1` to the port in `connection.json` (`$SESSION_INBOX_HOME` aware, via contracts `paths`) and adds the bearer per request. Vite 8's proxy has no per-request `router`, so a daemon that moves ports needs a Vite restart.
- U-006 — Basecoat CSS only (`basecoat-css/nova`), never its JS. Nova's tokens are overridden in `styles.css` with the mockup's warm neutrals plus four status hues (needs-you orange, working blue, ready green, failed red) as extra tokens; all text pairs chosen for ≥4.5:1 in both themes. Tailwind 4.3.5 for layout utilities.
- U-007 — Dark mode follows `prefers-color-scheme` (tokens redefined in a media query, and `@custom-variant dark` remapped to the media query) instead of Basecoat's `.dark` class, so no JS toggling and the Tauri webview just follows the system.
- U-008 — System font stack (SF on macOS) at 13 px base, not the mockup's Inter: native feel in a menu-bar app and no web-font fetch from a 127.0.0.1 page.
- U-009 — The Model never derives lifecycle/queue/priority: tabs filter on `item.queue`, "Working" lists sessions whose daemon `state` is `running`, counts are `snapshot.counts` verbatim. Optimistic UI is limited to `submission: Sending` (disables buttons); the item itself changes only via the action response or a delta.
- U-010 — Stable list order: the queue shows items in the daemon's snapshot order; ids first seen in a delta are appended (never inserted), so a new item never moves what you're looking at. A fresh snapshot (startup/reset) re-adopts daemon order.
- U-011 — Routing without Foldkit's router: initial `#/item/<id>` arrives as a flag, later changes via a `hashchange` subscription (the shell navigates the hash). Selecting in the UI writes the hash with `history.replaceState` (no history spam, no hashchange loop). `?view=compact` is read once at boot.
- U-012 — Compact view (popover) is plain links: rows go to `/#/item/<id>`, the footer to `/`. Which window ends up showing it is the shell's call. The mockup's "pause notifications" button is omitted: there is no API for it.
- U-013 — ⌘K / ⌘↵ / ⌘⌫ via `Dom.streamFromKeyBindings`. ⌘↵ is "primary action of the detail pane" (send answers → allow once → send reply); ⌘⌫ only denies when a permission is shown and is suppressed while typing so it still deletes text in fields.
- U-014 — Form state per item: one `AnswerDraft {selected, other}` per question; single-choice uses `@foldkit/ui` RadioGroup (one submodel per question), multi-choice uses Checkbox; typing an "other" answer clears a single-choice pick. Drafts are PUT 500 ms after the last edit (versioned debounce); on load the daemon draft (`{answers, reply}`) wins over recorded answers. A detail refetch for the same item keeps in-progress input.
- U-015 — Idempotency keys are `crypto.randomUUID()` generated inside each Command's `execute` (one per user intent), per Foldkit's rule that randomness lives in Commands.
- U-016 — `@foldkit/ui` used: RadioGroup, Checkbox, Textarea, Menu (snooze/dismiss/mute), Dialog + Combobox (⌘K jump), Toast. Not used: VirtualList (queues are tens of items; variable-height cards; not worth the experimental surface) and Query (a plain Command + `DaemonClient` is the adapter). Tree, tabs, cards, approval card, context strip, timeline and badges are custom.
- U-017 — Toasts only for delivery-related confirmations: action accepted (answers/reply/decision/snooze), outbox entries that turn delivered/failed between two detail loads, "Opened in Claude"/"resume command copied" (`url: null`, G-013), and daemon errors. Native alerts stay with the shell (G-012).
- U-018 — The session tree is a flat ARIA tree (`role=tree`, treeitems with `aria-level`, roving tabindex) rather than nested groups: one keydown handler per row, simple focus math, same visual indentation.
- U-019 — A delta that touches the selected item (or its session) refetches `/v1/items/:id`, since deltas carry rows but not detail (outbox, timeline, approval).

## Shell

- S-001 — Windows load the daemon's external URL (`http://127.0.0.1:<httpPort>/`, popover `/?view=compact`); no bundled UI, no IPC, no token passing. `frontendDist` is a placeholder page in `src-tauri/offline/`, so the Rust build never depends on the UI. The shell re-reads `connection.json` every 5 s (health loop) and re-navigates any window whose origin no longer matches, so a daemon restart on a new port recovers on its own (verified against the fake daemon).
- S-002 — No capabilities file: the shell only uses Rust-side APIs, so the remote pages get zero Tauri IPC permissions.
- S-003 — Notifications use `mac-notification-sys` 0.6.15 directly (what `tauri-plugin-notification` wraps via notify-rust), not the plugin: the plugin exposes no click/action callbacks on macOS, while mac-notification-sys blocks per notification until click/action/dismiss, so each notification gets its own thread. One action = `SingleAction`; several = a dropdown on the main button (macOS shows one main button). `click`/`open`/`answer` POST acted, then show the main window at `#/item/<itemId>`; `allow`/`deny` POST acted and open nothing. `Info.plist` sets `NSUserNotificationAlertStyle=alert` (legacy notifications need it to show buttons). Unverified: visual delivery and real clicks (no GUI session during the build; `sample` showed the library polling `deliveredNotifications`, so a notification reached usernoted). Needs a human check on a real desktop; NSUserNotification is deprecated and may stop working in a future macOS.
- S-004 — "Pause notifications" is a local toggle that drops non-critical `notify` messages (the daemon still counts them delivered). Critical ones always post.
- S-005 — Dev/test runs (`SESSION_INBOX_HOME` set) never touch launchd or the login item: no `launchctl kickstart`, no autostart registration. In production the shell registers the login item once (marker file in the app data dir, so a user who removes it is not re-enrolled) and kicks the daemon once per offline episode.
- S-006 — Popover hides on blur; a 300 ms guard stops the tray click that caused the blur from re-opening it. Closing the main window hides it; only the tray's Quit exits. Dock icon hidden (Accessory policy).
- S-007 — Bundle is ad-hoc signed (`signingIdentity: "-"`), `--bundles app` only. Enough to run locally; notifications, the login item and deep-link registration may behave differently until a Developer ID signature plus notarization.
- S-008 — The shell's `/v1/stream?client=shell` connection sends no `since`: it only needs live `notify` and `badge`, and a missed badge is corrected by the next one.
- S-009 — Rust is ~450 lines including ~60 of unit tests and comments, over the doc's 300 target: notifications, health, SSE parsing and window plumbing each need a few dozen lines. Split into `main.rs`, `daemon.rs`, `notify.rs`.

## Phase 0 spike findings

- P-001 — Phase 0 had no model access: child `claude -p` runs fail auth inside the agent sandbox. Live-proven: SessionStart/UserPromptSubmit/SessionEnd payloads, `--resume`, worktree `cwd`. Everything else is static (binary/asar) and marked unverified; `scripts/spike/live.ts` runs the rest. Fixtures hold only real payloads. Why: don't build contract tests on invented data.
- P-002 — Hook payload deltas vs `contracts/hook.ts`: add optional `prompt_id` (UserPromptSubmit, SessionEnd, others), `duration_ms` (PostToolUse), `last_assistant_message`, `background_tasks`, `session_crons` (Stop, SubagentStop), `session_title`, `agent_type` (SessionStart). `permission_mode` is absent on SessionStart/SessionEnd, so keep it optional. `cwd` is the realpath. Keep decoding with `decodeHookPayload` so unknown fields survive.
- P-003 — Classify Notification by `notification_type`: `permission_prompt` and `worker_permission_prompt` become approval items; `idle_prompt` ("Claude is waiting for your input") and `agent_needs_input` become "needs you"; `agent_completed` is informational; `elicitation_response`, `elicitation_complete`, `auth_success`, `auth_storage_failure`, `push_notification`, `plugin_notification`, `computer_use_enter`, `computer_use_exit` are ignored for the inbox. Unknown types default to ignored, never to an alert. Why: the CLI's emitted set (static); an unknown type must not spam.
- P-004 — AskUserQuestion answer mode: default **`updatedInput`** (`allow` + `updatedInput = tool_input + answers:{"<question text>":"<option label>"}`; multi-select comma separated), because `call()` reads `input.answers` and the result text is the clean "Your questions have been answered" message. Verify with the PostToolUse for AskUserQuestion: its `tool_response.answers` must equal what was sent; if the answers are empty or the tool still prompted, the daemon switches that session to **`denyWithReason`** (`deny` + reason `The user answered via Session Inbox: <question> → <label>`) and remembers it per runtime. Make the mode a daemon setting (`ask_answer_mode`). Unverified live (see spike.md Q3): `requiresUserInteraction` may stop a hook allow from skipping the card.
- P-005 — `--resume <id> -p` keeps the same `session_id` and appends to the same transcript (live). Its SessionStart arrives with `source:"resume"` and `entrypoint:"sdk-cli"`: never create a new session or change a desktop session's runtime from it. Use it only when the session has no running turn. Concurrent mid-turn resume is untested, so stay conservative. Desktop sessions: acceptable for idle/waiting sessions; prefer the PreToolUse path for live questions (G-015).
- P-006 — "Open in Claude" links: desktop session `claude://code/continue?session=<hostSessionId>` (`local_<uuid>` from `CLAUDE_CODE_HOST_SESSION_ID`); CLI session `claude://resume?session=<session_id>` (imports into desktop) with the copy-`cd … && claude --resume <id>` fallback; project-only fallback `claude://code/new?folder=<cwd>`; unknown id lands on `/epitaxy` (harmless). Needs the desktop app logged in and deep links enabled. Static; test one link after install.
- P-007 — Desktop Code-tab sessions load user-level hooks: the session spawn passes `settingSources:["user","project","local"]` and does not set `disableAllHooks`. Static plus the live evidence of this agent session. Verify live after install with one desktop session and a `local_<uuid>` hostSessionId in the event.
- P-008 — PreToolUse decisions: besides allow/deny/ask there is `defer` (print mode only, ignore it). The hook must answer within its own `timeout` (set it above the daemon hold, default hold 120 s so `timeout: 130`) and answer `ask` itself on expiry rather than relying on timeout semantics, which are unverified (a timed-out hook is expected to fall through, but a "hook did not finish, call not run" path exists for cloud sessions). Desktop registers its own PreToolUse hook (`permissionDisplay`); interaction with ours is unverified.
- P-009 — Worktree payloads carry the worktree path as `cwd` (live). Project grouping must resolve the main worktree via `git rev-parse --git-common-dir` in the daemon (G-019); never group by `cwd` string.
- P-010 — Notification hooks cannot be triggered in `-p`; the first real Notification fixture must come from a desktop/CLI interactive session after install (`inbox-hook record`).
