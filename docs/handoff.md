## Verified live, and how

- **The default approval mechanism, on a real desktop-app session** (Claude Code 2.1.321, P-022). A Read outside the project, a question, an Edit (with its diff preview and Claude's sentence before it) and a Bash `rm` were each answered from the inbox. Allow and answers took effect about 30 ms after the decision while Claude's own prompt was on screen; the denied command didn't run and Claude reported the deny message ("Denied by the user in Session Inbox."). `PermissionRequest` fires for desktop Code-tab sessions and its `permission_suggestions` are `addRules` entries.
- **Always allow, on the GA release install** (P-023): Always allow on a Read outside the project echoed Claude's suggested rule, and the next Read in that folder ran with no prompt at all. The observing beta inbox showed the same items and cleared them when GA answered.
- **Classic mode: answers reach a held `AskUserQuestion`.** A real desktop session (Claude Code 2.1.321): the answer arrived as `allow` plus `updatedInput.answers`, and the `PostToolUse` result matched 27 ms later. `questions.answerModeByRuntime` stayed empty (P-012).
- **Classic mode: Allow and Deny release a held Bash** 0.5 s after the decision. The first Bash of a session takes Claude about 10 s itself, however long it was held (P-013).
- **Open in Claude lands on the exact desktop session.** The deep link was opened through the daemon and the desktop app's window layout then showed that session focused (P-017).
- **Titles** come from the desktop app's `custom-title` transcript lines (P-015). **The approval preview** shows a real diff, and its context is read again when an item opens (D-066).
- **The update path**, end to end under the real launchd against a local release server: `bun scripts/e2e-update.ts`, 39 checks, run in the default mode. A held call blocks the automatic update, it applies after 30 s of quiet, hooks fail open during the swap, a corrupted download is refused, and the real settings and GA/beta plists are unchanged afterwards (H-031).
- **After the review round**: the unit tests, the smoke test (which now restarts the daemon twice while a request is live) and the screenshot script (through headless Chrome, with the token) pass, and the reinstalled apps on this Mac connect.
- **Notification delivery without the app's buttons**: with the app reporting `denied`, the setup check's test notification went out as `via: fallback`, and `usernoted` logged it as displayed (P-019).

## Things to know

- Reinstalling or restarting the daemon leaves any request to Claude's own prompt, which is harmless: in the default mode nothing was paused, and a classic hold lapses to `ask`. `session-inbox holds <ga|beta>` restarts both daemons, so switch when nothing is waiting.
- Replies to idle sessions and Haiku titles need the `claude` CLI to be logged in; the desktop app's login isn't shared. Without it the reply box says so and offers **Open in Claude**.
- `scripts/e2e-update.ts` is the only script that uses the real launchd (an isolated label under `/tmp`). Run it only when nobody is reinstalling beta, or its closing check on the real plists trips.
- When behaviour changes, update the matching page under `site/content/` in the same change. The site deploys on every push to `main` that touches `site/**`, `README.md`, `DECISIONS.md` or `VERSION`.
- Roll back a bad install with `session-inbox uninstall --yes` (dry run without `--yes`), or restore the `settings.json.bak-<timestamp>` file the installer leaves beside `~/.claude/settings.json`.
